내가 맡은 부분

내가 맡은 부분은 LocalGuard 안에서 게임 프로세스에 로드되는 DLL 변화를 확인하는 게임 내부 모듈 무결성 검사다. 외부 프로그램이 게임에 위험한 권한으로 접근하는지 보는 부분은 은지님 담당이고, 나는 게임 프로세스 안에 어떤 DLL이 들어왔는지를 본다.

이번에 module_integrity를 실제로 구현했다. Windows Toolhelp API로 게임 프로세스의 DLL 이름, 전체 경로, base address, image size를 읽고, 첫 번째로 정상 수집된 DLL 목록을 기준선으로 저장한다. 그 다음부터 목록을 다시 읽어서 새로 추가된 DLL, 사라진 DLL, 같은 경로인데 주소나 크기가 바뀐 DLL을 구분한다.

새 DLL이나 변경 DLL이 나오면 공통 ArtifactInspector와 ArtifactCache를 사용해 파일의 SHA-256, 디지털 서명 상태, 게시자를 확인한다. 검사 결과는 DLL 전용 allowlist와 비교한다. allowlist는 이름만 같다고 통과시키지 않고 이름과 SHA-256을 반드시 같이 본다. 필요하면 경로, 서명 상태, 게시자까지 모두 맞아야 통과하도록 만들었다.

허용되지 않은 변화는 session_id, player_id, module, timestamp_ms, evidence, reasons, raw_score의 일곱 필드로 JSONL에 기록한다. module 값은 external_access로 통일하고, evidence 안의 submodule 값으로 module_integrity를 넣어서 외부 프로세스 접근 결과와 구분한다. 로컬 기록이 성공한 뒤 shared의 내구성 있는 대기열에도 같은 이벤트를 넣는다. 이 프로그램이 바로 사용자를 차단하거나 게임을 종료하지는 않는다. 관찰 사실과 점수만 만들고, 중앙 스코어링이 다른 탐지 결과와 합쳐 최종 의심도를 판단한다.


전체 구조

LocalGuard의 external_access는 공통 계층, 외부 프로세스 접근 탐지, 게임 내부 모듈 무결성 탐지로 나뉜다.

공통 계층에는 ProcessLocator, ArtifactInspector, ArtifactCache, detection_result, jsonl_writer가 있다. ProcessLocator는 가능하면 launcher가 전달한 정확한 PID를 사용하고, 그렇지 않으면 실행 파일 이름이 유일할 때만 게임을 고른다. PID와 프로세스 생성 시간을 함께 비교해 재실행도 구분한다. ArtifactInspector는 EXE나 DLL의 SHA-256, Authenticode 서명 상태, 게시자를 확인한다. ArtifactCache는 SHA-256이 실제로 같을 때만 비용이 큰 서명 검사 결과를 재사용한다. detection_result는 팀에서 정한 일곱 필드 형식을 만들고 검증하며, jsonl_writer는 결과 한 건을 JSON 한 줄로 저장한다.

외부 프로세스 접근 탐지는 다른 프로세스가 게임에 VM_WRITE, VM_OPERATION, CREATE_THREAD 같은 위험 권한으로 핸들을 열었는지 확인한다. 게임 내부 모듈 무결성 탐지는 게임 안에 로드된 DLL 목록의 변화를 확인한다. 관찰 대상은 다르지만 게임 PID 찾기, 파일 신뢰 정보 확인, 결과 형식은 같아서 공통 계층을 재사용한다.

내 모듈의 실행 순서는 다음과 같다.

게임 프로세스 찾기
→ PID와 생성 시간으로 현재 게임 인스턴스 확인
→ Toolhelp API로 현재 DLL 목록 수집
→ 첫 성공 목록이면 기준선 생성
→ 이후 목록이면 마지막 성공 목록과 비교
→ 새 DLL과 변경 DLL만 SHA-256, 서명, 게시자 검사
→ 엄격한 allowlist 비교
→ Detector가 이유와 raw_score 생성
→ 공통 일곱 필드 JSONL 기록
→ 중앙 스코어링에서 다른 탐지 신호와 종합

코드는 역할별로 나눴다. module_sensor는 Windows에서 DLL 목록이라는 사실만 수집한다. baseline은 이전 목록과 현재 목록을 비교한다. detector는 그 변화와 파일 신뢰 정보를 보고 점수를 만든다. runner는 게임 탐색부터 기록까지 전체 순서를 연결한다. 센서와 판정을 분리했기 때문에 Windows API 부분을 바꾸더라도 점수 정책 전체를 다시 만들 필요가 없고, 가짜 스냅샷을 넣어서 각 계층을 따로 테스트할 수 있다.


기준선 관련 설명

기준선은 정상 파일 인증 목록이 아니라 이전 상태와 현재 상태를 비교하기 위한 목록이다. 첫 스냅샷의 DLL을 전부 새 DLL로 처리하면 Windows DLL과 언리얼 엔진 DLL이 한꺼번에 탐지되어 오탐이 발생한다. 그래서 기본 모드에서는 첫 스냅샷을 변화 이벤트로 만들지 않는다.

기본 모드만 사용하면 LocalGuard보다 먼저 들어온 DLL이 첫 기준선에 섞일 수 있다. 그래서 LocalGuard를 게임보다 먼저 실행하고, 검토된 정적 allowlist가 있으면 시작 목록 감사가 자동으로 켜지게 만들었다. 빈 allowlist에서도 강제로 시험하려면 --audit-initial-snapshot을 사용한다. 이 감사는 allowlist에 없는 초기 DLL을 전부 기록하므로 목록을 먼저 검토해야 한다. 처음 보였다는 이유만으로 자동 allowlist에 넣지는 않는다.

DLL 목록 수집이 잠깐 실패해도 빈 목록으로 처리하지 않는다. 빈 목록으로 기준선을 바꾸면 다음 검사에서 원래 있던 DLL 전체가 새로 추가된 것으로 오인되기 때문이다. 실패한 검사는 기준선을 갱신하지 않고 마지막으로 성공한 목록을 유지한다.

게임이 재실행되면 PID와 프로세스 생성 시간을 비교하고, 다른 게임 인스턴스로 확인되면 이전 기준선을 폐기한 뒤 새 기준선을 만든다. PID만 비교하지 않는 이유는 Windows가 종료된 프로세스의 PID를 다시 사용할 수 있기 때문이다.


점수 설명

새 DLL은 정상 프로그램에서도 생길 수 있으므로 변화 자체는 1점으로 낮게 잡았다. 같은 경로의 로드 주소나 이미지 크기 변화도 정상 unload/reload와 ASLR 때문에 생길 수 있어 1점으로 둔다. 미서명이면 1점, 서명 검증 실패면 2점을 더한다. 서명 조회 실패는 권한이나 환경 문제일 수도 있어서 추가 점수를 주지 않는다. 정확한 allowlist 항목과 일치하면 이벤트를 만들지 않는다. 이 점수는 바로 밴하는 점수가 아니라 정상 로그와 테스트 로그를 ReplayAnalyzer로 비교한 뒤 조정할 원시 점수다.


module_integrity와 memory_integrity 차이

module_integrity는 DLL 목록, 새로 로드된 DLL, DLL 파일의 해시·서명·게시자, allowlist를 담당한다. memory_integrity는 이미 로드된 모듈의 .text 코드 영역 변조, 인라인 훅, vtable이나 ExecFunction 같은 함수 포인터 변조를 담당한다. 둘의 범위를 이렇게 나누지 않으면 같은 이상 신호가 중복 점수화될 수 있다.


현재 완료한 범위와 검증이 더 필요한 부분

module_integrity 안의 DLL 센서, 기준선 비교, 파일 검사, allowlist, Detector, standalone Runner, 단위 테스트, 공통 JSONL 출력, shared 전송과 정상 종료 처리를 구현했다. Launcher에도 외부 핸들 감시와 DLL 감시를 각각 등록했고, 두 프로세스에 같은 session, player, t0와 정확한 게임 PID가 전달된다. 센서 오류가 연속으로 발생하면 종료 코드 2로 끝나 Launcher와 Watchdog가 감시 불능 상태를 알 수 있게 했다. 앞으로 실제 게임의 정상 로그와 승인된 양성 테스트 로그를 더 모아 점수를 재조정하고, 게임 업데이트마다 정상 DLL allowlist를 검토해야 한다.


짧게 답할 때

“전체 구조는 수집, 기준선 비교, 파일 신뢰 검사, 판정, 출력, 중앙 점수화로 나뉩니다. 제 담당은 게임 프로세스의 DLL 목록을 기준선과 비교해서 새 DLL이나 변경 DLL을 찾는 부분입니다. 새 변화가 나오면 공통 모듈로 해시, 서명, 게시자를 확인하고 엄격한 allowlist와 비교합니다. 결과는 공통 JSON으로 기록하고, 이 모듈에서 바로 차단하지 않고 중앙 스코어링에서 다른 근거와 합쳐 판단합니다.”


자주 나올 수 있는 질문과 답

Q. 기준선에 들어간 DLL은 전부 정상인가?
A. 아니다. 기준선은 목록 변화를 찾는 비교 자료다. 자동 allowlist가 아니며, LocalGuard보다 먼저 주입된 DLL은 별도 정적 기준 비교로 보완해야 한다.

Q. DLL 이름만 정상 파일처럼 바꾸면 통과하지 않나?
A. 이름만 보지 않는다. 이름과 SHA-256을 필수로 비교하고, 필요한 항목은 경로, 서명 상태, 게시자 조건까지 모두 확인한다.

Q. 게임을 재실행하면 이전 기준선을 계속 쓰나?
A. 이름 기반 모드는 PID와 생성 시간을 비교해서 새 기준선을 만든다. launcher가 정확한 --game-pid를 넘긴 운영 방식에서는 재실행할 때 launcher가 LocalGuard도 새 PID로 다시 실행해야 한다.

Q. DLL 목록 수집이 실패하면 어떻게 하나?
A. 빈 목록으로 처리하지 않고 마지막 성공 기준선을 유지한다. 그래야 다음 검사에서 정상 DLL 전체가 새 DLL로 오인되지 않는다.

Q. 서명된 DLL이면 무조건 정상인가?
A. 아니다. 서명은 보조 정보다. 서명됐어도 allowlist에 없는 실행 중 변화는 이벤트로 남기며 다른 근거와 함께 본다.

Q. 탐지되면 바로 게임을 종료하나?
A. 현재는 종료하거나 밴하지 않는다. 설명 가능한 이벤트와 raw_score를 만들고 중앙 스코어링이 여러 신호를 합쳐 판단한다.

Q. 캐시는 파일 교체에 속지 않나?
A. 경로, 크기, 수정 시간만 믿지 않고 캐시 조회 때 SHA-256을 다시 계산한다. 실제 내용 해시가 같을 때만 비용이 큰 서명 검사 결과를 재사용한다.

Q. manual-map DLL도 잡나?
A. Toolhelp 모듈 목록에 등록되지 않는 manual-map 방식은 이 센서 하나만으로 놓칠 수 있다. 메모리 맵 검사나 실행 가능 사설 메모리 영역 탐색 같은 별도 센서가 필요하다.

Q. 새 DLL 하나가 나오면 핵으로 확정하나?
A. 아니다. 정상 오버레이나 드라이버도 DLL을 나중에 로드할 수 있어서 새 DLL 자체는 낮은 점수만 준다. 서명, 해시, allowlist와 다른 탐지 신호를 같이 본다.

Q. 디스크 파일 해시가 정상이라면 메모리도 정상인가?
A. 아니다. 디스크 파일 해시는 파일 식별 근거일 뿐이다. 메모리 안의 코드 변조는 memory_integrity가 별도로 검사해야 한다.
